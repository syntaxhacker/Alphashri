# Design System Storybook

Run it:

```bash
bun run storybook        # http://localhost:6006
bun run build-storybook  # static output in storybook-static/
```

The catalog is grouped under **Design System / …** only. The current built
`storybook-static/index.json` has **384 story entries and 93 autogenerated docs
pages**. The source audit (`docs/COMPONENT_AUDIT.md`) scans 93 story files and
parses the same 384 entries. The built index is the authoritative id list —
check a story id against it before adding a link.

It is built with Solid’s `solidStory()` helper (`src/stories/solidStory.ts`)
because Storybook’s `html-vite` renderer expects a DOM node. Each story mounts a
Solid root into its own host, uses the real Tailwind/CSS-variable tokens, and is
disposed by the preview **`beforeEach` hook — in story mode only**. Docs mode
renders a whole group at once, so disposing roots there would blank every story
but the last. There is no `afterEach` teardown.

Docs and accessibility panels are enabled via `@storybook/addon-docs` and
`@storybook/addon-a11y`. The addon is a manual review panel; automated checks
run in CI: a happy-dom axe smoke suite (`src/test/a11y-smoke.test.tsx`), a
real-browser axe pass (`node scripts/storybook-a11y.mjs`, representative stories,
serious/critical violations fail the job), scoped UI coverage
(`bun run test:coverage:ui`), and the catalog guard after a Storybook build.
Browser axe checks rendered contrast and roles, not keyboard focus order/trap or
pixel diffs — those still need a manual or Playwright walkthrough. There is no
viewport toolbar addon. The palette is dark-only and single-sourced in
`src/ui/palette.ts` — stories read CSS variables and token modules, never a
second palette or a light/dark toggle.

Overview links use the manager form `../?path=/story/<id>` with `target="_top"`,
so they leave the preview iframe instead of nesting another Storybook.

## Coverage

### Overview
- Purpose, principles, token summary, story-group map and component index.
- `Overview.stories.tsx` is the only design-system page that does not use
  `FamilyLanding.tsx`; the other **12 family pages** (Foundations, Typography,
  Layout, Inputs, Data display, Feedback, Overlay, Navigation, Shared
  primitives, App primitives, Portal, Misc) share its
  `FamilyPage`/`FamilyHero`/`FamilyChip`/`ComponentIndex`/`SpecimenPanel`/
  `FamilyFooter` helpers.

### Foundations
- Raw anchors, semantic tones, `SURFACES` and border tokens
- Real `Text`/`Title` type scale and mono/tabular numerals
- Real spacing ramp `xs=4 / sm=8 / md=16 / lg=24 / xl=32`
- Real Paper/Card radius scales, shadows and reduced-motion density

### Typography
- All Text tones, weights, alignment, uppercase, line height, truncation,
  line clamping, `component`/`span` and numeric treatment
- Title order/size/component overrides
- Anchor, inline/block Code, ordered/unordered List/ListItem

### Layout
- `Box`, `Flex`, `Stack`, `Group`, `ToolbarRow`, `Center`
- `Paper`, `Card`, `Divider`, `ScrollArea`, `Collapse`
- `SimpleGrid`, `Grid`/`GridCol`, `Row`/`Col` with real span/offset/order,
  wrapping, responsive columns and 390px behavior
- Real mixed-height control rows; surfaces and radius comparison

### Inputs
- `Button` variants/sizes/states, `ActionIcon`, `UnstyledButton`

  `PasswordInput`, `DatePicker`

### Form
- `FormField` — unstyled field shell with a render prop; owns ids and
  `aria-describedby`/`aria-invalid` wiring for label, description, required and

### Feedback

## Conventions

1. Use the existing `solidStory(() => …)` helper, never a separate renderer.
2. Prefer real `@/ui` components and CSS variables; do not fork a palette into
   story-local constants.
3. Show state variants in one story when possible (sizes, tones, disabled,
   loading), so a reviewer can inspect the matrix at a glance.
4. Use fixed widths only where the component is intrinsically narrow. Use the
   `Responsive390` layout story or a 390px host for narrow-screen review.
5. Add a `Design System/…` story when a new primitive enters `src/ui/index.ts`.
   Feature composites (Options Dock, Replay, Market, Patterns, Reports) keep
   their screenshot/Playwright evidence and can get their own stories in a
   later feature-story pass.
6. Stories must use real components. Never recreate a primitive with a
   hand-positioned `Box` when the real component exists.

## Current limits

- The catalog covers the reusable `@/ui` surface, shared app primitives and the
  design-token pages. It does **not** yet story-ify every feature composite
  (options dock, replay, patterns rail, sector pages, etc.); those are
  intentionally next.
- Automated a11y now spans happy-dom and real-browser axe over representative
  stories, but it is not a full WCAG audit (no keyboard focus-order/trap or
  screen-reader walkthrough) and there is **no visual regression baseline**.
  A static Storybook build cannot assert pixel diffs by itself; the PR
  screenshot rule (real app at 1600/390) still applies.
- The old `Terminal/*` stories were consolidated into
  `Design System/App primitives`; there are no duplicate Terminal groups.
