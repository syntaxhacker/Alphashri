# Storybook — Alphashri design system

Storybook is the living reference for the local `@/ui` primitives and the
design tokens they read. It is **documentation of existing work**, not an audit
or a coverage guarantee: a story exists where someone wrote one.

```bash
bun run storybook        # dev server on http://localhost:6006
bun run build-storybook  # static output in storybook-static/
```

The built catalog is authoritative. `storybook-static/index.json` lists every
story and doc id, and is the source of truth for links — check an id against it
before adding a link to the Overview page.

## 1. What is actually in the catalog

Everything lives under the single top-level section **`Design System/*`**:
**67 stories and 13 autogenerated docs pages**. There is no `Primitives/*`,
`Composites/*`, `Patterns/*`, `Examples/*` or `Terminal/*` hierarchy.

All thirteen files are under `src/stories/design-system/`. Each has
`tags: ["autodocs"]`, which is where the 13 `*-docs` entries in `index.json`
come from — docs pages are generated, not hand-written.

The `Overview` story is the map: it links to every one of the 67 stories, grouped
by the table above. Its links use the manager URL form
`../?path=/story/<id>` with `target="_top"` so navigation leaves the preview
iframe instead of nesting a second Storybook inside it.

## 2. Rendering model

Stories are authored for `@storybook/html-vite`, which expects a DOM node. Solid
does not have a portable runtime, so every story is mounted through
`solidStory(() => …)` from `src/stories/solidStory.ts`. That helper creates a
host element, renders one Solid root into it, and records a disposer.

`.storybook/preview.ts` (TypeScript, **not** `.tsx`) owns cleanup: its
`beforeEach` hook calls `disposeSolidStories()` **only in `viewMode === "story"`**.
Docs mode renders all stories of a group at once, so disposing roots before each
there would blank all but the last one. There is no `afterEach` hook.

`.storybook/main.ts` wires the framework and two addons:

- `@storybook/addon-docs` — the docs pages and description blocks.
- `@storybook/addon-a11y` — an in-panel accessibility checker for manual review.

There is no Storybook test runner, no axe gate in CI, no Chromatic/Loki visual
diffing and no viewport toolbar addon. CI runs lint, typecheck and the normal
Vitest suite; Storybook is a static build plus a human review surface.

## 3. Theme: dark only

The palette is dark-only and single-sourced in `src/ui/palette.ts`.
`solidStory` paints its host from `palette.BG_COLOR` / `palette.TEXT_COLOR`, and
`.storybook/preview.ts` derives the `canvas` and `panel` backgrounds from
`palette.BG_COLOR` / `palette.SURFACE`. There is no light/dark toolbar toggle and
no virtual-colour switching in stories.

Components use the running CSS variables (`var(--color-fin-*)`) and real `@/ui`
primitives. Story files never introduce a second palette or hardcode a hex;
where a raw token is needed it is read from `@/ui/palette`. The same rule applies
to the app: a hex outside `palette.ts` is review-blocking.

## 4. Narrow-screen review

Responsive review is a story, not a toolbar setting: **`Design System/Layout →
Responsive390`** (`design-system-layout--responsive-390`) renders a 390px host
with real `Row`/`Col` spans, `ToolbarRow` wrapping and `useMediaQuery` branches.
Grid/row matrices, control rows and `SimpleGrid` sit alongside it in the Layout
group. To see breakpoint branches take over, resize the Storybook canvas itself
to 390px — there is no device-viewport addon installed.

## 5. Interactive stories

Controls are real Solid signals, not fixed values with a no-op handler.
`Slider`, `RangeSlider`, `SegmentedControl` and `DatePicker` in the Inputs group
are each driven by `createSignal` and a real setter, so dragging, switching and
picking a date update the readout in place. Controlled inputs carry a visible
label (or `aria-label` on a wrapping `role="group"`) and keep the same
props/contract they have in app code.

Prefer the same pattern for new interactive stories: signal in the component
passed to `solidStory`, real `onChange`, no synthetic fixed values.

## 6. Authoring conventions

- Use `solidStory(() => …)`; never a second renderer or a hand-built host.
- Use real `@/ui` components and CSS variables. Do not fork a palette into
  story-local constants, and do not recreate a primitive with a positioned `Box`
  when the real component exists.
- Show state variants in one story when it helps review (sizes, tones, disabled,
  loading) rather than splitting them into trivial one-prop stories.
- Keep data domain-real: NSE symbols, ₹ amounts, IST timestamps, negative P&L,
  empty collections. No lorem ipsum or "John Doe".
- No story calls a production API. Stories render from props/tokens only and
  work with zero backend running.
- Verify story ids against `storybook-static/index.json` when editing links in
  the Overview page; stale ids silently open a blank manager tab.

## 7. What is intentionally out of scope

Feature composites (Options Dock, Replay, patterns rail, sector pages, report
panels) keep their screenshot/Playwright evidence; they are not story-ified
here. There is no per-component `play()` interaction layer, no co-located
`Select.stories.tsx` exemplar, no line-count limit on story files, and no
promise of one story per primitive state. Add stories when a primitive or
shared app primitive actually enters the design system, and keep the Overview
map in sync.
